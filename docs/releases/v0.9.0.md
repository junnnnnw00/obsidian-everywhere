# Obsidian Everywhere v0.9.0 — Reviewable Git for local vaults

Obsidian Everywhere turns linked notes into focused AI context and makes that
context available to agents wherever they run. Graph traversal, full-text and
optional local semantic search, attachment extraction, and guarded edits still
operate against the vault on your own machine—even when the MCP client is on an
external server connected through authenticated HTTP or an HTTPS tunnel.

v0.9.0 adds stable, opt-in Vault Git tools. An agent can inspect and checkpoint
changes in a vault that is already managed with Git without receiving a remote
shell or unrestricted Git access. Git remains off by default, and each
deployment chooses its capability level explicitly.

## Vault Git

- `git_status`, `git_diff`, and `git_log` provide bounded, local-only repository
  inspection in `read` mode.
- `git_commit` creates an unsigned commit from an exact list of reviewed files
  in `commit` mode.
- `git_push` publishes the reviewed `HEAD` only to its existing upstream through
  an operator-pinned, credential-free HTTPS destination in `push` mode.
- Commit and push use a preview followed by a five-minute, one-use approval.
- The service never fetches, pulls, changes branches, accepts arbitrary
  refspecs, or exposes a general-purpose `git_exec` tool.

The Git repository can be the vault root or one real folder inside the vault.
This is useful when the complete vault should remain searchable but only one
project folder is version-controlled. For example:

```bash
export OBSIDIAN_VAULT_PATH="/Volumes/SanDisk/jwhong"
export OBSIDIAN_EVERYWHERE_TOKEN="<long-random-token>"
export OBSIDIAN_EVERYWHERE_READONLY=true
export OBSIDIAN_EVERYWHERE_GIT_MODE=read
export OBSIDIAN_EVERYWHERE_GIT_REPO_PATH=DSLab

npx -y --package obsidian-everywhere@0.9.0 obsidian-everywhere-http
```

Here, graph, semantic, search, and file tools use the full
`/Volumes/SanDisk/jwhong` vault, while Git paths are relative to
`/Volumes/SanDisk/jwhong/DSLab`. Start in `read` mode and confirm `git_status`
and `git_log` from the remote client before enabling writes.

Push requires the ordinary write gate as well as an exact remote-to-URL mapping:

```bash
export OBSIDIAN_EVERYWHERE_READONLY=false
export OBSIDIAN_EVERYWHERE_GIT_MODE=push
export OBSIDIAN_EVERYWHERE_GIT_ALLOWED_PUSH_REMOTES=origin=https://github.com/owner/vault.git
```

The complete setup and transport-specific environment names are documented in
the [Vault Git guide](https://github.com/junnnnnw00/obsidian-everywhere/blob/v0.9.0/docs/git-vault.md).
For an external agent, first configure the
[Remote Vault Bridge with ngrok](https://github.com/junnnnnw00/obsidian-everywhere/blob/v0.9.0/docs/ngrok-remote.md),
verify the vault identity and read-only tools, and only then raise the write
capability.

## Safety model

Vault Git uses fixed command shapes and argument arrays rather than a shell. It
validates the configured repository boundary, metadata layout, exact paths,
file modes, attributes, proposed Git tree, branch and upstream state, and the
exact push destination. It captures the vault, selected repository, and `.git`
identities at startup and rechecks them before every Git subprocess. Hooks,
repository-local includes and HTTP/network overrides, external diff and clean
filters, unsafe object layouts, symlinks, submodules, unresolved merges, and
histories that exceed review limits fail closed. Commit content, outgoing
commit messages, and changed blobs are checked for common secrets before an
approval can be used. Push rechecks the reviewed state and uses a compare-and-
swap lease so a changed remote-tracking ref cannot be silently overwritten.

## Verification

The release adds real temporary-repository integration coverage for status,
diff, log, commit, push, nested repository selection, approval expiry and
one-use behavior, SHA-256 repositories, unusual filenames, and adversarial Git
configuration. The CI matrix runs the Git integration suite on Linux, macOS,
and Windows in addition to lint, formatting, type checking, the complete test
suite, build, package-content, and Docker runtime checks. Release publishing
now also verifies that the npm package, lockfile, MCP Registry metadata,
runtime version, and `v`-prefixed Git tag all agree before either registry is
updated.
